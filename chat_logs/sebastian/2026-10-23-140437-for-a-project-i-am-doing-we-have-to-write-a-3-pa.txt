  Abstract

  Introduction

  LIME is a popularly used model-agnostic explainability method for black box
  models. The runtime of LIME depends on the number of perturbation samples and
  inference cost of the black-box model to which it is being applied, while
  the quality of explanations degrades as feature space grows.

  Studies have examined LIME's instability and proposed variations upon LIME,
  but there is a lack of guidance on how cost and quality might scale together
  as dimensionality and model complexity increase.

  This paper's purpose is to investigate LIME cost/quality scaling across
  multiple models on large tabular datasets, measuring runtime against
  stability and fidelity to identify where additional computations stop
  improving explanation quality.

  Methodology

  3.0 Study Design

  This is a controlled computational experiment characterizing how LIME’s cost
  and quality scale with the number of samples (N) and features (d) using a
  factorial design (3 models x 4 values of d x 5 values of N x 5 repeats).

  The three research questions this experiment aims to address are:

  How does runtime scale with N and d per explanation?

  How does quality change with N and d?

  How does the black-box model change cost/quality trade-offs?

  The unit of analysis is 30 explained instances – 5 instances per class,
  controlled and evaluated via ranked subsets and a fixed kernel width at
  0.75·√300 to prevent differences in computation per instance run.

  3.1 Dataset & Preprocessing

  The chosen dataset 'UCI HAR' consists of 561 continuous features, and 6
  classes – selected for its high dimensionality and continuous features.

          The dataset has a subject-based train/test of 70/30 , so that there
  is no leakage between subjects.

  Random state is set to 42

  Subsets for 'd' are nested using a seeded random permutation.  LIME perturbs
  only the d chosen features and the remianing instances rest at their original
  values, so the model always receives all 561. Five explained instances are
  chosen per true class from the test set.

  Sample sizes have been split into 500, 1000, 2500, 5000, 10000. Random state
  is set to 42, and a background sample of 2000 training rows is passed to
  LIMETabularExplainer.

  Each explanation reports on 10 features and LIME is re-run 5 times upon each
  sample size with different explainer seeds, since Jaccard across seeds needs
  several runs.

  3.4(a) The cost of LIME

  Controlled variable: Number of perturbations - LIME’s cost is driven by how
  many times it calls the black-box model.

  Measured outcome: Wall-clock time per explanation, split by stage.

  Total time per explanation is roughly:

  T(N, d) ≈ T_sample(N, d) + T_predict(N, d, model) + T_weight(N, d) + T_fit(N,
  k)

  N: num_samples ex: (500, 1000, 2500, 5000)

  d: number of features (54 in Covertype)

  T_sample: generating N perturbations over d features. With the default
  discretisation, this scales roughly as O(N·d).

  T_predict: N black-box predictions. This term depends heavily on the model
  and is where your four models will differ most.

  T_weight: distance and kernel computation, O(N·d).

  T_fit: fitting the weighted ridge surrogate on k selected features. Watch
  feature_selection: the default 'auto' uses forward selection when k ≤ 6,
  which fits many surrogates and can noticeably increase this term. Fix the
  setting and state it in the paper.



  Cost is only meaningful next to a quality measure at the same budget. For
  each (model, d, N), we paired cost with:



  Stability: Jaccard overlap of the top-k features across seeds for the same
  instance.

  Local fidelity: the surrogate’s weighted R² (explanation.score), or agreement
  between local_pred and the true model output.

⏺ Your notes are mostly right. Two points need rewording: stability has not
  levelled out at high d for every model, and "linear" needs a small qualifier.
  Below I go through each point (✅ correct, ⚠️ partly right, ❌ wrong), with

  Runtime

  "Runtimes increase linearly as samples increase" ✅ (with a refinement)
  - A straight line T = a + b·N fits each model × d combination almost perfectly
    (R² ≥ 0.993, and 1.000 for most).
  - More precisely, runtime is affine: a fixed overhead per explanation plus a
    constant cost per sample.
    - For XGBoost at d=500 the overhead is about 53 ms, plus about 86 ms per
      1,000 samples.
  - This explains the log-log exponent of about 0.72–0.77 (below 1) from the
    earlier output. The fixed overhead makes small N look relatively expensive.
  - So 20× more samples (500 → 10k) costs only about 8–10× more time, not 20×.

  "More features → runtime increases more per sample" ✅ This is an interaction
  effect between N and d. Here is the cost per 1,000 samples (the slope):

  ┌─────┬───────┬───────┬───────┐
  │  d  │  LR   │  RF   │  XGB  │
  ├─────┼───────┼───────┼───────┤
  │ 50  │ 9 ms  │ 14 ms │ 17 ms │
  ├─────┼───────┼───────┼───────┤
  │ 500 │ 78 ms │ 84 ms │ 86 ms │
  └─────┴───────┴───────┴───────┘

  - 10× more features gives roughly a 5–8× steeper slope.
  - The fixed overhead also grows with d, from about 4–15 ms to about 46–53 ms.

  "LR fastest, RF second, XGBoost last" ✅
  - The ranking holds in every one of the 20 N × d settings.
  - All 12 runtime comparisons at N=5,000 are statistically significant
    (Holm-corrected p < 0.05).

  1. LIME fits a linear surrogate on only 10 features while perturbing 50–500.

  2. Quartile discretisation turns each continuous feature into 4 bins, which

  Graph terminology you can use

  - Small multiples / faceted panels: one column per d. Rows are runtime,
    fidelity and stability (from lime_overview.png).
  - 95% bootstrap confidence bands: the shaded areas. Overlapping bands mean the
    difference is uncertain.
  - Hollow markers: N ≤ d settings, shown but excluded from the lines.
  - Affine / linear scaling, slope (cost per sample), intercept (fixed
    overhead).
  - Scaling exponent: the slope on a log-log plot. Below 1 is sublinear.
  - Plateau / saturation, elbow (knee) point, diminishing returns: for the
    fidelity and stability curves.
  - Monotonic / non-monotonic: XGB stability is non-monotonic in d, because
    d=300 is its best setting.
  - Crossover / rank reversal: the RF → XGB switch in stability.
  - Cost–quality frontier (Pareto front): in cost_vs_quality.png, the curve that
    sits higher at the same runtime is the better trade-off.
  - Interaction effect: d changes the effect of N, and the reverse.

  Points worth adding

  1. Diminishing returns in numbers. For XGB at d=500:
     - 1k → 2.5k samples adds +0.23 Jaccard for +0.13 s.
     - 5k → 10k adds only +0.03 for +0.43 s.
     - That is about 20× more seconds per unit of stability gained. This
       directly answers your research question about where extra computation
       stops helping.
  2. Fidelity and stability saturate at different points. Fidelity flattens
     around 2.5k samples, while stability keeps improving at a growing cost.
     "More samples" therefore mainly buys consistency, not accuracy of the
     surrogate.
  3. The N ≤ d failure. At N=500 with d=500, explanations are effectively random
     (Jaccard 0.00–0.03). This is a concrete lower bound on how many samples
     LIME needs.
  4. Convergence to a 50k-sample reference. Getting within about 90% of the
     reference ceiling generally takes 10k samples. The one exception is XGB at
     d=300, which needs 5k. LR and RF at d ≥ 300 never get there.
  5. Practical recommendation: the cost–quality plot shows RF gives the best
     quality per second at low d, and XGB at high d. LIME's default of 5k
     samples is past the fidelity plateau but not yet at the stability plateau.
  6. Model accuracy doesn't predict explanation quality. LR is the most accurate
     model (95.5%) but gives the least stable and least faithful LIME
     explanations.

     C. Why the results make sense (or don't)
